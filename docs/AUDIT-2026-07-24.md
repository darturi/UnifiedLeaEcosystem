# System audit — vulnerabilities, logic errors, and brittle points (2026-07-24)

> **Scope:** the whole `lea-ecosystem` monorepo — the FastAPI adapter, the vendored
> prover, the Overleaf companion + extension, and the React UI — reviewed against
> `issue_address` @ `674e76b` (plus the uncommitted per-run-model change in the
> working tree).
>
> **Method:** source read of every adapter module, the prover's tool/sandbox layer,
> the companion's server seam, and the UI's rendering path; claims verified against
> the code and, where cheap, executed (regex and path-join behaviour were run
> directly). **Analysis only — no source files were changed.**
>
> **Baseline:** all suites are green at the time of writing — 462 adapter pytest
> tests, the Overleaf companion suite, and the UI frontend suite. Every finding
> below is therefore something the existing tests do **not** cover.
>
> **Relationship to prior work:** `apps/overleaf-extension/AUDIT.md` (2026-07-06)
> and [SYSTEM-REVIEW-2026-07-10.md](SYSTEM-REVIEW-2026-07-10.md) covered the
> companion and the design-level shape of the Overleaf path. Their load-bearing
> fixes still hold (atomic serialized JSON writes, the companion's origin
> allowlist, the ledger status engine). This audit therefore centres on the
> **adapter and the prover seam**, which have grown a lot since and have had less
> adversarial attention.

## What is genuinely solid

Worth stating, because it sets the bar the findings are measured against:

- **The concurrency primitives are well-reasoned.** `db.write()` (BEGIN IMMEDIATE),
  the `timeline.id`-as-ordering-key merge, and `runregistry.try_admit` (check-is-the-claim)
  are correct, and their docstrings explain the failure modes they replaced with
  measured numbers. This is unusually good.
- **The "SQL owns proof content" inversion is consistently enforced.** There is no
  surviving code path that stores a git pointer as proof content.
- **Migrations + pre-migration snapshots** (`migrations.py` / `backup.py`) are real,
  and the "snapshot fails → migration doesn't run" policy is the right call.
- **The companion's origin hygiene is exemplary** — it not only sets a narrow CORS
  allowlist but *rejects* requests carrying an unrecognized browser `Origin`
  (`server.mjs:3119-3128`), because a cross-site simple request still executes
  server-side. That reasoning is correct, and the adapter does not have it (S1).
- **No XSS in either UI.** KaTeX runs with `trust: false`, the React markdown path
  segments before rendering, and every `innerHTML` in `content.js` is a static
  template with dynamic values assigned via `textContent`.

## Security

<a id="s1"></a>
### S1 — The adapter has no authentication and no `Origin`/`Host` validation (High)

**Where:** `adapter/app/main.py:20-26`, `adapter/app/routes/sessions.py:336-362`,
`adapter/run_api.py:12-19`

The adapter binds `127.0.0.1:8001` and adds `CORSMiddleware` with a two-entry
allowlist. That is the *entire* access-control story for an API that can start
runs which execute arbitrary shell commands, delete projects, push to GitHub, and
read/write files. Two gaps make the CORS allowlist much thinner than it looks:

1. **The WebSocket endpoint is not covered by CORS at all.** Browsers do not apply
   the same-origin policy to WebSockets, and `lsp_socket` performs no `Origin`
   check. Any page the user visits can open
   `ws://127.0.0.1:8001/api/sessions/<id>/lsp`, which spawns a `lake serve`
   process per connection. Worse, the client controls the document URI and the
   proxy's rewrite is a blind prefix (`lsp_proxy.py:61-75`): a client sending
   `file:///../../../../etc/passwd` becomes
   `file:///<lake_root>/../../../../etc/passwd`, so LSP diagnostics/hover become
   an arbitrary-file read primitive. Session ids are UUIDs, but they leak into
   the Overleaf pane and the UI's URL, and the endpoint 404s in a distinguishable
   way.
2. **CORS does not defend against DNS rebinding.** An attacker domain that
   re-resolves to `127.0.0.1` makes every request same-origin from the browser's
   point of view, so no CORS check fires at all. The companion's `Host`-agnostic
   sibling has the same shape but at least rejects unknown `Origin`s outright.

The companion already implements the correct pattern
(`companion/server.mjs:3119-3128`, "a cross-site simple request still executes
server-side even when the page can't read the response"). The adapter needs the
same belt: reject any request carrying a browser `Origin` not on the allowlist,
validate `Host` against `localhost`/`127.0.0.1:8001`, and add an `Origin` check to
the WebSocket handshake. A shared loopback token (already sketched — the companion
threads an `apiKey` through `buildHeaders`) would close it properly.

`lsp_proxy.py:24-26` already carries the right warning ("⚠️ If the adapter is ever
exposed to untrusted remote users, reintroduce a container per session") — the
point of this finding is that a browser tab *is* an untrusted remote user.

<a id="s2"></a>
### S2 — `_GITHUB_REMOTE_RE` doesn't pin the host: push exfiltrates the GitHub PAT (High)

**Where:** `adapter/app/routes/projects.py:90`, `:339-366`; `adapter/app/gitstore.py:45-58`

```python
_GITHUB_REMOTE_RE = re.compile(r"^https://[\w.\-]+/[\w.\-]+/[\w.\-]+$")
```

The error message says *"Enter an https GitHub repo URL"*, but the pattern accepts
**any** host. Verified: `https://evil.example.com/a/b` matches. `_push_project`
then calls `push_to_github(repo, remote_url, token)`, and `_inject_token` embeds
the credential in the URL:

```
https://x-access-token:<PAT>@evil.example.com/a/b
```

git sends that in the `Authorization` header of the initial `GET /info/refs`
request, so the attacker's server receives the user's GitHub Personal Access
Token before any push is even attempted. The whole project's contents follow.

There is no auth on `PUT /api/projects/{id}/git/remote` either, so this is
reachable by anything that can reach the API (see S1), not just by a user who
mistypes a URL.

#### ✅ Fixed (2026-07-24)

Defended at two layers, because input validation alone leaves the stored row as an
unguarded second entry point.

**1. The credential boundary** — `gitstore._inject_token` (`gitstore.py:45-77`) now
refuses to embed the token unless the URL is `https` *and* its host is in the new
`GITHUB_CREDENTIAL_HOSTS` allowlist (`github.com`, `www.github.com`,
`gist.github.com` — the last is required by `ghimport`'s private-gist clone path).
Anything else comes back untouched, so the push proceeds unauthenticated and fails
rather than authenticating to a stranger. `http` is now excluded as well: the
credential must not travel in cleartext, and nothing in the codebase builds an
`http` GitHub URL.

This is the layer that actually matters. `_inject_token` is the one place the token
enters a URL, so putting the check there means every present and future caller
inherits it — the previous shape depended on whichever route happened to build the
URL having validated it.

**2. Route input validation** — `_GITHUB_REMOTE_RE`
(`routes/projects.py:90-108`) is pinned to `^https://(?:www\.)?github\.com/…$`, and
each path segment must start with a word character or hyphen so `..` can't appear
as an owner or repo. `_push_project` (`routes/projects.py:373-386`) re-checks the
stored value at the moment the credential would be used, because a row written
before the pin — or by anything that touches `projects.remote_url` directly — must
not become a delivery target either. Non-http(s) remotes (local paths, ssh) skip
that check, since they can't carry the token; that keeps the existing
push-to-local-bare-repo tests meaningful.

**Tests:** `test_gitstore.py` — `_inject_token` embeds for github.com/gist, and a
parametrized case asserts the token appears *nowhere* in the result for the
exfiltration target, a `github.com.evil.example.com` suffix-lookalike,
`raw.githubusercontent.com`, cleartext `http`, and an ssh remote; plus an
end-to-end push to a dead non-GitHub https host asserting the token is absent from
the error. `test_routes_projects.py` — the route rejects five hostile URL shapes
and leaves `remote_url` unset, still accepts both legitimate shapes, and a
directly-stored legacy remote is refused at push with `push_to_github`
monkeypatched to fail loudly if it is reached at all.

**Note for reviewers:** the suffix-lookalike case (`github.com.evil.example.com`)
is why this is a host-equality check on `urlparse().hostname` rather than a
`startswith`/`in` test on the URL string.

### S3 — Path traversal in the standalone check/rebuild/verify endpoints (High)

**Where:** `adapter/app/routes/sessions.py:400-416`

```python
rel = path or _latest_proof_path(session_id)
...
return str(repo / rel), rel
```

`rel` comes straight from the request body (`PathRequest.path`) and is joined onto
the repo with **no containment check**. `repo / "../../../../etc/passwd"` resolves
outside the session directory — verified. Three endpoints use it:

- `POST /api/sessions/{id}/lean-check` — runs Lean over the target file and returns
  `detail`, which for a non-Lean file is a parse error that quotes source lines.
- `POST /api/sessions/{id}/rebuild` — runs `lake build` against it.
- `POST /api/sessions/{id}/verify` — runs SafeVerify against it.

`lean-check` with `author` set additionally writes a new `code_step` row for the
traversed path, polluting the timeline.

The correct guard is *three functions away in the same file*:
`write_file_session` does exactly this (`sessions.py:193-197`), and
`filesystem._safe_abs` and `routes/projects._resolve_repo_file` each implement it
again. `_resolve_proof_path` is the one that was missed.

#### ✅ Fixed (2026-07-24)

`filesystem._safe_abs` was **promoted to public `filesystem.safe_abs`**
(`filesystem.py:39-60`) and `_resolve_proof_path` now goes through it
(`routes/sessions.py:400-433`), raising `400` on an escape. That also inherits the
`IGNORED_DIRS` guard, so `.git/config` and the `.lake` build tree are out of reach
too — neither was in the original report, both were reachable.

Promoting the helper rather than inlining a fourth copy is the point of the fix.
The containment logic existed in three places (`write_file_session`,
`filesystem._safe_abs`, `routes/projects._resolve_repo_file`) and the bug was a
*missing* copy, not a wrong one. One shared function means the next path-joining
route can't reintroduce it by omission; the docstring says so explicitly.

`_resolve_proof_path` now also returns the **normalized** relative path
(`abs_path.relative_to(repo.resolve()).as_posix()`), which is the same form
`bridge._relativize` writes into `timeline.path` — so the `latest_code_step_for_path`
lookups keyed on it are unaffected, and an un-normalized spelling
(`./Lea/Other/../Misc/p.lean`) now resolves onto the same code step instead of
silently missing it. That is a small bonus fix.

**Not done — and deliberately:** the report also suggested rejecting non-`.lean`
paths. I left that out. Every current caller passes `.lean`, but the default path
comes from the session's latest code step, and I could not establish from the code
that a non-`.lean` step can never reach these endpoints (the cascade path in
particular is driven by the companion). Containment is the security fix and is
provably behaviour-preserving; an extension filter is a behaviour change that
wants its own reasoning. Worth revisiting.

**Tests:** `test_routes_sessions.py` — a parametrized case drives all three
endpoints with five escape shapes (plain traversal, traversal behind a legitimate
prefix, an absolute path, `.git/config`, `.lake/...`) with `interface_check`,
`interface_verify`, and `interface_rebuild` all monkeypatched to raise if reached,
so the assertion is "the toolchain never ran", not merely "a 400 came back"; plus
a case pinning that the `author=` branch refuses *before* writing its cascade
code_step, and one asserting legitimate in-repo paths still resolve and normalize.

**Verified against the pre-fix code:** with the guard reverted, all 7 new tests
fail. They are pinning the bug, not the implementation.

<a id="s4"></a>
### S4 — Prompt injection from a mirrored Overleaf document reaches an unsandboxed shell (High)

**Where:** `prover/lea/tools.py:430-447` (`bash`), `:143-156` (`read_file`),
`adapter/app/bridge.py:1049-1051` (`gate=None` when autonomous),
`adapter/app/projects.py:214-234` (mirrored `.tex` folded into the context)

This is a chain, and each link is individually documented as an accepted tradeoff.
Composed, it is the sharpest exposure in the system:

1. The extension mirrors the Overleaf project's `.tex` sources into
   `.lea/files/overleaf/` and `compose_context_message` tells the agent to
   "Consult them for the prose statements, notation, and definitions". The `.tex`
   is attacker-influenced content whenever the Overleaf project has a collaborator,
   is shared from a link, or is a template.
2. Every Overleaf-driven run is **autonomous by construction** (D19): `run_events`
   is called with `gate=None`, so no tool ever pauses for approval.
3. `bash` is `subprocess.run(command, shell=True)` with no allowlist, no jail, and
   only `cwd` set. `cwd` is a starting directory, not a boundary.
4. `read_file` has **no confinement whatsoever** — unlike `write_file`/`edit_file`,
   which go through `_sandboxed_write_path`. So the model can read
   `~/.ssh/id_rsa`, the monorepo `.env`, and `config/lea.local.toml` (every
   provider key and the GitHub PAT, in plaintext).

The `_sandboxed_write_path` guard (`tools.py:162-198`) is thoughtful, but it
protects one tool while `bash` — in the same default toolset — bypasses it
entirely (`bash("cp /tmp/x /anywhere")`). It is worth being explicit in the
design docs that the write sandbox is a *typo/hallucination* guard, not a
security boundary, so nobody later reasons from it as if it were one.

**Fix (in increasing cost):** (a) confine `read_file` the same way writes are
confined — this is cheap and closes the credential-read half; (b) exclude the
mirrored `.tex` from the context for autonomous runs, or wrap it in an explicit
"this is untrusted data, never instructions" delimiter; (c) gate `bash` even in
autonomous mode behind an allowlist of `lake`/`git`/`ls`-shaped commands;
(d) container-per-run, which `lsp_proxy.py`'s D63 note already anticipates.

### S5 — `/artifacts/retire` deletes any file in the project repo (Medium)

**Where:** `adapter/app/routes/projects.py:606-622`

The docstring says "a retry deletes the previous proof file", and the 404 message
says "No recorded file at that path" — but the only check is `absolute.is_file()`.
The artifact index is never consulted. So the endpoint will happily `unlink()`
`lakefile.toml`, `.lea/instructions.md`, or a `.lean` file belonging to a
different session, then commit the deletion.

The restore path only helps if the caller kept the `retire_commit`, and
`restore` refuses when the path is occupied — so a wrong retire is effectively
one-way for the caller.

**Fix:** require the path to match a row in `store.list_artifacts_for_scope(project_id)`
(or at minimum require a `.lean` suffix under the namespace dir) before unlinking.

### S6 — Secret files are written non-atomically, at default permissions, with no value escaping (Medium)

**Where:** `adapter/app/settings.py:503-559`, `adapter/app/subagent_overrides.py:68`,
`scripts/env.mjs:84`

Three problems in the same write path:

1. **Not atomic.** `path.write_text(...)` truncates first. A crash or a full disk
   between truncate and write leaves `config/lea.local.toml` empty — i.e. every
   provider key and the GitHub token gone. The companion learned this lesson and
   uses temp+rename (`atomicWriteJson`); the adapter did not.
2. **Default permissions.** Neither `lea.local.toml` nor `.env` is chmod'ed; with a
   typical umask they land at `0644`, world-readable on a shared machine.
3. **No value escaping beyond `\` and `"`.** `_toml_scalar` escapes those two
   characters only. A key value containing a literal newline (paste accident,
   or any client hitting `PUT /api/settings` directly — only the three
   first-class providers get format validation, everything matching
   `*_API_KEY` is stored verbatim) produces a basic TOML string spanning two
   lines. `tomllib.loads` then raises on **every** subsequent request, because
   `load_config`, `permission_tier`, `github_token`, and
   `configured_provider_keys` all re-parse the file on every call with no
   try/except. The adapter 500s on essentially every endpoint until the file is
   hand-repaired.

**Fix:** write via temp+`os.replace` with `0o600`; escape control characters in
`_toml_scalar` (or use a TOML writer); wrap the four config readers so a parse
failure degrades to defaults with a loud log rather than a hard 500.

<a id="s7"></a>
### S7 — Upload body is fully buffered before the size cap is checked (Medium)

**Where:** `adapter/app/routes/projects.py:719-728`, `adapter/app/uploads.py:99-114`

```python
data = await file.read()          # entire body into memory
... uploads.save_upload(..., data, ...)   # MAX_UPLOAD_BYTES checked here
```

The 25 MB cap is enforced *after* the whole body is resident. A single multi-GB
POST OOMs the adapter — and with it every in-flight run, since the prover runs
in-process. There is no `Content-Length` pre-check and no streaming read.

**Fix:** check `request.headers["content-length"]` up front, and read in chunks
with a running total that aborts past `MAX_UPLOAD_BYTES`.

<a id="s8"></a>
### S8 — `git` subprocesses have no timeout and no `GIT_TERMINAL_PROMPT=0` (Low)

**Where:** `adapter/app/gitstore.py:212-222`

```python
proc = subprocess.run(["git", *args], cwd=repo, capture_output=True, text=True)
```

No `timeout=`, and the environment is inherited. `push_to_github` against a remote
that challenges for credentials (e.g. the token is empty or the host isn't GitHub)
makes git block on a terminal prompt forever, pinning the request thread. Every
other git call has the same shape.

`ghimport._clone` got this right (`timeout=CLONE_TIMEOUT_SECONDS`) — `gitstore`
just wasn't updated to match.

**Fix:** `timeout=` on `_git`, plus `env={**os.environ, "GIT_TERMINAL_PROMPT": "0",
"GIT_ASKPASS": "", "GCM_INTERACTIVE": "never"}`.

## Correctness

<a id="c1"></a>
### C1 — Global usage totals, and therefore the spend cap, only count 100 sessions (High)

**Where:** `adapter/app/store.py:218` (`limit 100`), `:1702-1759` (`usage_stats`),
`adapter/app/settings.py:305-312`, `adapter/app/bridge.py:957-975`

`_list_sessions` ends with a hard-coded `limit 100`. `usage_stats()` computes its
`global` block by summing the Python list `list_sessions()` returns — so
`global.cost_usd` is the cost of the **100 most-recently-updated sessions**, not
of all of them.

Three things consume that number:

- `settings.spend_limit_reached()` → the `402` guard on `POST /api/runs`;
- `bridge.check_spend_cap()` → the mid-run cap that stops a run at a turn boundary;
- the Settings page's `current_spend_usd` and the whole Stats page.

Once a user passes 100 sessions, the reported spend **decreases** as old sessions
fall out of the window, so a configured `max_spend_usd` silently stops being
enforced — exactly the failure mode the cap exists to prevent. The `daily` and
`models` rollups in the same function are computed with proper SQL aggregates over
the full table, so the Stats page will show a `global` total that disagrees with
its own daily chart.

#### ✅ Fixed (2026-07-24)

Two new full-table aggregates in `store.py` (`store.py:1702-1760`):

- **`global_usage()`** — one query counting every session, every non-code timeline
  row, and every run's tokens/cost. `usage_stats()["global"]` is now just this.
- **`total_spend_usd()`** — a single `SELECT coalesce(sum(cost_usd), 0) FROM runs`.
  Kept separate from `usage_stats()` deliberately: the cap is checked at every turn
  boundary and on every `UsageUpdated` event, and routing that through the full
  stats payload is both what made it wrong *and* a heavy per-event query.

Both spend-cap readers now use the scalar — `settings.current_spend_usd`
(`settings.py:305-310`, which `spend_limit_reached` and so the `402` on
`POST /api/runs` sit on) and `bridge.check_spend_cap` (`bridge.py:957-975`).
`settings_payload` no longer builds the whole stats payload just to read one number.

**`_origin_rollup` was fixed too**, and it wasn't in the original write-up. It folded
the same truncated page, and its docstring promised *"aggregated from the same
`sessions` rows the `global` totals come from, so the two always agree"* — which
was true, and was the problem: they agreed while both were wrong. It is now a
`GROUP BY origin` aggregate over the full `sessions`⋈`runs` join, so the promise
holds for the right reason (`store.py:1774-1820`).

`usage_stats()["sessions"]` is **still** the 100-row page — truncating a rendered
table is fine, and a comment now says so. The rule the fix encodes: *a total over
"everything" is a SQL aggregate over everything; a paginated list is for rendering,
never for arithmetic.*

**Tests:** `test_store.py` — 120 sessions and the global block reports all 120
while `stats["sessions"]` still returns 100, plus an assertion that `global` now
agrees with the `daily` and `models` rollups beside it (those were already correct

### C2 — `_project_has_active_runs` cannot detect a run in a session that already has code (High)

**Where:** `adapter/app/projects.py:487-488`, `adapter/app/store.py:1665-1691`

```python

    return any(session.get("status") == "running" for session in store.list_project_sessions(project_id))
```

But `_derive_session_status` returns `"running"` **only when the session has no
code steps yet**:

```python
if code_step_count:
    ... return the verdict          # "proved" / "ok" / "error" / ...
if has_active_run:
    return "running"
```

That is deliberate (D14: status is a working-copy verdict, not run lifecycle) —
the guard just read the wrong field. Any project session that has ever written a
file reports `proved`/`ok`/`error` while a run is live.

The consequence is severe: `migrate_project_namespace` uses this as its only
safety interlock, then rewrites every `.lean`/`.md` in the repo and
`shutil.move`s the whole directory. Renaming a project's namespace while an agent
is mid-run moves the working tree out from under it — the run's `write_file` calls
recreate the old path, the code steps point at a directory that no longer exists,
and the migration's own `lake` re-check races the agent's writes.

The correct signal is right there on the same row: `_list_sessions` already
computes `active_run_count` (`store.py:193-196, 230, 238`).

#### ✅ Fixed (2026-07-24)

New `store.project_has_active_run(project_id)` (`store.py:1402-1424`) — a direct
`SELECT 1 FROM runs JOIN sessions … WHERE status IN ('pending','running') LIMIT 1`
— and `projects._project_has_active_runs` (`projects.py:487-496`) now delegates to
it.

Taking the query rather than the `active_run_count` column was the deliberate
choice: the column is only available on the `_list_sessions` aggregate, so using it
would have meant running that 100-row six-subquery aggregate to answer a boolean —
and it inherits the same `limit 100` truncation as [C1](#c1), so a project's
101st-oldest session would have been invisible to the interlock. A safety check
should not be able to miss things because a list was paginated.

The join goes through **`sessions.project_id`, not `runs.project_id`**, and the
docstring says why: `repo_for_session` picks the on-disk repo from the session's
project tag, so that is the link that decides whose working tree a run is writing
to — which is exactly what this interlock protects.

**Tests:** `test_projects.py` — the load-bearing case is a project session that has
a code step *and* a running run, asserting both that its derived status is `"ok"`
(not `"running"` — pinning the D14 behaviour the old predicate misread) and that
the interlock fires anyway; the pre-code case the old check *did* catch, so the fix
can't regress it; the terminal-run case; the end-to-end migration refusal
(`project_busy`/409, with assertions that the repo did **not** move and the index
still names the old namespace); and an idle-project rename that must still succeed,
so the guard doesn't become a blanket refusal.

**Verified against the pre-fix code:** with the predicate restored, the
established-session detection and the migration refusal both fail — the migration
runs to completion and moves the repo.

**Still open, related:** the check is a TOCTOU — a run can be admitted between the
interlock and the `shutil.move`. Narrowing that needs the same
atomic-`UPDATE`-and-branch treatment as [C7](#c7), and is out of scope here.

### C3 — `_promote_winner` overwrites the canonical proof before re-verifying it (High)

**Where:** `adapter/app/bridge.py:837-855`, `adapter/app/collation.py:139-160`

```python

verdict = _lean_check_file(str(canonical))    # then checks it

    logger.warning(...)
    return None                               # ...and leaves the bad file in place
```

The re-verification guard is the right idea — the docstring even explains why the

the write, and the failure path doesn't roll back. Two ways that loses work:

1. If a proof already existed at `<namespace>/<candidate-name>.lean` (a previous

**Fix:** promote to a temp path, `lean_check` there, and only `os.replace` into

### C6 — A post-completion bookkeeping error rewrites a successful run to `failed` (Medium)

### C7 — `interrupt_run` TOCTOU against the dispatcher (Medium)

**Where:** `adapter/app/routes/runs.py:212-231`, `adapter/app/bridge.py:136-178`

```python
if run["status"] == "pending" and not runregistry.registry.is_active(run_id):
    store.update_run(run_id, "failed", ...)
```

The dispatcher independently reads `store.get_run(run_id)`, sees `pending`, calls
`try_admit`, and spawns `run_lea`, which sets `status = "running"`. Interleave the
two and you get: endpoint reads `pending` → dispatcher admits and spawns →
endpoint's `is_active` check happens to run before the registry insert lands, or
the endpoint's `update_run("failed")` lands after `run_lea`'s `update_run("running")`.

Both orderings are wrong in a visible way: either the run is reported "interrupted"
and then keeps executing (and billing), or it is marked `failed` while running and
then flips back to `running`, defeating the recovery invariant that a `failed` row
is terminal.

The cooperative `request_stop` flag is set first, so the run *will* stop at its
next turn boundary — but "next turn boundary" on a fresh run can be a full model
call away, and the endpoint has already told the client it's over.

**Fix:** make the transition atomic — a single `UPDATE runs SET status='failed'
WHERE id=? AND status='pending'` and branch on `rowcount`, so exactly one of the
two writers wins.

## Concurrency and liveness

<a id="x1"></a>
### X1 — The single dispatcher head-of-line blocks; `LEA_MAX_CONCURRENT_RUNS=4` doesn't deliver 4 (High)

**Where:** `adapter/app/bridge.py:131-199`

```python
while True:
    run_id = _run_queue.get()
    while True:                       # ← inner loop, this run only
        ...
        admission = registry.try_admit(...)
        if admission.outcome == ADMITTED: ... break
        if admission.outcome == SESSION_BUSY and admission.incumbent_run_id:
            request_stop(admission.incumbent_run_id)
        time.sleep(0.1)               # ← spins here, holding the queue
```

There is exactly one dispatcher thread, and it does not pull the next queue entry
until the current head is admitted. So:

- **`SESSION_BUSY` blocks unrelated sessions.** A follow-up in session A waits for
  A's incumbent to stop cooperatively — which can be a full model call away, or
  never if the incumbent is stuck on an unanswered approval (up to
  `APPROVAL_DECISION_TIMEOUT_SECONDS = 900`). Meanwhile runs queued for sessions
  B, C, D sit behind it with three free slots.
- **`AT_CAPACITY` is fine on its own** (nothing else could start either), but
  combined with the above, the effective concurrency of the system is well below
  its configured capacity in exactly the multi-chat scenario Phase 6 raised the
  default to 4 for.
- **`request_stop` is re-issued at 10 Hz** for the whole wait. It's idempotent, so
  harmless, but it's a symptom: the loop has no state, it just re-decides.

The registry itself is correct and per-run — the bottleneck is entirely the
dispatcher's shape.

**Fix:** don't block on a run that can't be admitted. Requeue it (with a small
backoff) and take the next item, or run one dispatcher per admitted slot. Issue
`request_stop` once per supersede decision, not once per poll.

**Related leak:** `request_stop` uses `_stop_events.setdefault(run_id, Event())`
(`bridge.py:84-86`), so calling `POST /api/runs/{unknown}/interrupt` creates an
`Event` that is only popped in `run_lea`'s `finally`. A run that never starts
leaves the entry forever. `_session_allowlists` (`bridge.py:248`) is likewise never
cleaned. Both are small, but both are unbounded in a long-lived process.

### X2 — Concurrent runs in one shared project repo race on `git add -A` (Medium)

**Where:** `adapter/app/gitstore.py:96-105`, used from `bridge.py:1182`,
`uploads.py:172, 201, 329`, `projects.py:313, 484`, `filesystem.py:114`

`commit_all` does `git add -A` → `git diff --cached --name-only` → `git commit`.
Project sessions **share one repo** (D24), and up to 4 runs can be admitted at
once. Nothing serializes them. Two failure modes:

1. **`index.lock` contention.** Two concurrent `git add -A` in the same repo make
   one fail with `Unable to create '.git/index.lock'`; `_git` raises
   `GitStoreError`, which in `bridge.py`'s `ToolResulted` branch is unguarded and
   propagates to the outer handler — failing an otherwise-successful run.
2. **Cross-contamination.** `git add -A` stages *everything* in the repo, so run A's
   asset commit includes run B's half-written proof file, attributed to A's commit
   message. Harmless for correctness (SQL owns proof content) but it makes
   `git log` useless as an audit trail, and it's what makes the `.gitignore`
   guard in `ensure_overleaf_gitignore` load-bearing rather than belt-and-braces.

`prover/lea/tools.py:29-38` already has the right pattern — a per-`lake_root` lock
keyed in a dict — for exactly this class of problem.

**Fix:** a per-repo-path `threading.Lock` around `commit_all`, and pathspec-scoped
`git add -- <path>` instead of `-A`.

### X3 — `lake serve` leaks on non-disconnect pump failures; no cap on LSP sockets (Medium)

**Where:** `adapter/app/routes/sessions.py:353-362`

```python
try:
    await proxy.pump(websocket)
except WebSocketDisconnect:
    await proxy.stop()
```

`pump` has its own `finally: await self.stop()` (`lsp_proxy.py:196-197`), so the
common paths are covered — but the `await proxy.start()` block above it is not
inside the same guard, and any exception raised *between* `start()` succeeding and

**Nothing bounds how many of these can exist.** Each connection spawns a full

**Fix:** a `BoundedSemaphore` on concurrent proxies (the prover already does this
for cold checks — `_COLD_CHECK_CONCURRENCY`), reject over the cap with a close
code, and move `proxy.start()` inside a `try/finally` that stops it.

## Performance and scale

<a id="p1"></a>
### P1 — `RunBroker` buffers everything and rescans it 12.5×/second per subscriber (High)

**Where:** `adapter/app/runbroker.py:55-72`, `adapter/app/routes/runs.py:91-102`

```python
def events_after(self, cursor):
    return [e for e in self._events if e["seq"] > cursor]   # O(n), full scan
```

with

```python
pending = broker.events_after(cursor)
...
await asyncio.sleep(0.08)                                   # 12.5 Hz
```

Two compounding problems:

1. **The buffer holds every event for the run's life**, including one
   `assistant_delta` per streamed token *and* every `code_step` payload — which
   carries the **full file contents** (`bridge.py:1097`). A long run over a large
   proof buffers tens of MB; four concurrent runs multiply it. The module
   docstring's justification ("Runs are minutes long; holding their events in
   memory is cheap for this local/single-tenant adapter") is reasonable for
   counts but was not written with per-token deltas and whole-file payloads in
   mind.
2. **The scan is linear and repeated.** `seq` is exactly `index + 1`, so
   `events_after` could be `self._events[cursor:]` — an O(1) slice. As written,
   a 20 000-event run with two attached subscribers performs 500 000
   comparisons per second, in the event loop thread, for a stream that is mostly
   empty.

**Fix:** slice by index instead of filtering; coalesce `assistant_delta` frames
(the UI rebuilds the bubble from concatenation anyway); store code-step payloads
by reference (the row id) rather than by value, since the client can fetch the
bytes.

<a id="p2"></a>
### P2 — `check_spend_cap()` runs the full usage aggregate on every `UsageUpdated` (High)

**Where:** `adapter/app/bridge.py:957-975`, `:1139-1145`

```python
persisted = float(store.usage_stats()["global"]["cost_usd"])
```

called from `check_spend_cap`, which fires on **every `UsageUpdated` event and
every `TurnStarted`**. `usage_stats()` is not cheap: it runs `_list_sessions` — a
100-row aggregate with six correlated subqueries per row, including two that scan
`timeline` — plus two more GROUP BY aggregates over `runs`.

With four concurrent runs each emitting usage per model call, this is several
heavy queries per second against a single-writer SQLite database that is
simultaneously taking `BEGIN IMMEDIATE` write locks for every message and code
step. It is a self-inflicted contention source of exactly the kind
`get_run_status` was introduced to eliminate (`store.py:1006-1013`).

**Fix:** a dedicated `SELECT coalesce(sum(cost_usd),0) FROM runs` (which also fixes
C1), memoized for a second or two — the cap is a turn-boundary decision, it does
not need per-event freshness.

<a id="p3"></a>
### P3 — `session_detail` and `build_graph` are N+1 with a new SQLite connection per blob (High)

**Where:** `adapter/app/store.py:1234-1240` (`blob_content`), `:1265-1291`
(`_code_step_from_row`), `:1619-1623`; `adapter/app/graph.py:151-166`

`session_detail` reads the whole timeline inside one connection, then builds the
response *outside* it:

```python
code_steps = [_code_step_from_row(r) for r in rows if r["kind"] == "code"]
```

and `_code_step_from_row` calls `blob_content(...)`, which opens **its own
connection** (`with connect()`), executes one SELECT, and closes it. A session with
200 code steps opens 200 SQLite connections and materializes 200 full file
contents — to render a thread the UI mostly scrolls past.

`graph.build_graph` is worse: for each blueprint node it calls
`code_steps_for_project_path`, which returns *every* step for that file across the
project, each hydrating its own blob through its own connection — and then uses
only `steps[0]["check_status"]` and the session ids. A 30-node blueprint with 20
revisions per file is 600 connections and 600 full file reads per `/graph` request,
and the Overleaf pane polls `/graph`.

**Fix:** join `artifact_blobs` in the parent query (`LEFT JOIN artifact_blobs b ON
b.id = t.after_blob_id`) so content arrives with the row; add a
`code_steps_for_project_path(..., include_content=False)` variant for the graph;
consider paginating `session_detail`'s timeline.

<a id="p4"></a>
### P4 — Two polling SSE endpoints hold per-client DB query loops for up to 3 hours (Medium)

**Where:** `adapter/app/routes/runs.py:105-116` (`_passive_done`),
`adapter/app/routes/sessions.py:63-101` (`session_list_events`)

- `_passive_done` loops 36 000 times at 0.3 s (3 h), calling `store.get_run` — one
  connection open/close — each tick. Every browser tab that reattaches to an
  already-finished run gets one of these.
- `session_list_events` loops 10 800 times at 1 s, calling `sessions_digest()` per
  tick, per connected client.

Neither is wrong, but together they establish a floor of several SQLite
connections per second per open tab, against the same single-writer database that
runs are writing to. The digest design is good (cheap fingerprint, expensive query
only on change) — the cost is the polling itself.

**Fix:** back both with a shared in-process notification (the `RunBroker` already
is one; a module-level `asyncio.Event` bumped by `store` writes would serve the
session list), falling back to a much slower poll as a safety net.

<a id="p5"></a>
### P5 — `artifact_blobs` are only garbage-collected inside project deletion (Low)

**Where:** `adapter/app/store.py:552-556`

The orphan sweep runs only in `delete_project_cascade`. Loose sessions have no
delete path that touches it, and `upsert_user_code_step`'s coalescing explicitly
drops references to superseded blobs — so every debounced autosave that produced a
unique intermediate state leaves a permanently unreferenced blob holding a full
copy of the file.

Content addressing bounds duplicates, not orphans. Over months of editing this is
the fastest-growing table in the database, and the database is now the thing
`backup.py` copies on every migration.

**Fix:** run the same orphan sweep on session delete and on a periodic/startup
vacuum step.

## Maintainability

- **M1 — Dead git read path.** `gitstore.commit_write` is explicitly marked
  deprecated and exercised only by its own test; `snapshot`, `uncommitted_diff`,
  `head`, and `diff` are now reachable only from `restore_project_artifact_by_slug`'s
  fallback (`snapshot`) — the rest have no callers. Keeping them costs a reader's
  attention every time they wonder whether git still owns content.
- **M2 — `adapter/_deferred/`** holds four modules (`project_usage.py`,
  `project_assignment.py`, `project_unassignment.py`, and a test) outside the
  package. They are neither imported nor tested. Either revive or delete.
- **M3 — `LEA_MAX_CONCURRENT_RUNS` is undocumented.** It is read once at import
  from `os.environ` (`runregistry.py:59-68`) and appears nowhere in `.env.example`,
  so the only way to change the system's concurrency is an exported shell
  variable — which also means it does **not** pick up values from the root `.env`
  unless the launcher exports them. Given the default moved from 1 to 4, this
  deserves a line in `.env.example` and a note in `CLAUDE.md`'s config section.
- **M4 — Pydantic v1 call.** `routes/subagents.py:70` uses `request.dict()`; the
  suite emits a deprecation warning on five tests. `model_dump()` is the
  replacement.

## Suggested order of work

Grouped by "cheap and closes a real hole" first:

1. **S3** (add the containment check — a two-line change with a guard already
   written twice elsewhere), **S2** (anchor the host regex), **C9** (add one
   `DELETE`), **M4**.
2. **C1 + P2 together** — replacing `usage_stats()["global"]` with a real SQL sum
   fixes the spend-cap correctness bug and the hottest query in the system in one
   change. **C4** falls out of the same `limit` cleanup.
3. **C2** (one-line predicate fix, but it guards a `shutil.move` of a live repo),
   **C3** (promote-to-temp-then-replace), **C6** (guard the post-completion writes).
4. **P1** and **P3** — both are mechanical (index slice; join the blob) and both
   are the difference between "fine at demo scale" and "fine at real scale".
5. **X1** — the dispatcher reshape is the one structural change here, and it is
   what the concurrency work was for.
6. **S1 / S4** — the security posture question. These need a decision, not just a
   patch: is the adapter a single-user local tool (in which case add the `Origin`
   and `Host` checks and confine `read_file`, and write down that `bash` is
   trusted), or is it heading somewhere multi-user (in which case the
   container-per-run note in D63 needs to become a plan)?
